# Debugging and logging

The app explains itself through its logs and its copyable errors; a symptom that is not in a log gets a log line
before it gets a theory. This file says what the logs hold, how to get them off the phone, and how a bug goes from
Igor's phone to a closed issue. The test rungs are in [TESTING.md](TESTING.md); the spec is the
[user stories](stories/README.md).

## The logs

Grabber Native keeps one session log per launch, takes a report from a shake, and turns each report into an issue
([design spec](superpowers/specs/2026-10-04-swift-native-app-design.md), stories
[140–145](stories/08-reporting-problems.md)). The React Native app's call log, timer log and gist uploads went with
its code (2026-10-17); a gist it uploaded earlier still opens with `gh gist view <id> --raw`.

| Log | What it holds | How it reaches the Mac |
|---|---|---|
| **The session log** | every event below, one JSON line each | `just pull-logs` (below) |
| **Copyable errors** (BugKit's `BugProblemView`) | every user-visible error, with *Copy error*: the message first, then `context:`, `build:` and the state the caller passed, numbers as numbers; a copy logs `ui` copy_error with `where` | the clipboard |
| **The native build logs** (`native/Build/logs/`) | the whole xcodebuild output of the last `native-build-sim`, `native-sim-health` and `native-build-device` (`build-sim.log`, `sim-health.log`, `build-device.log`), Xcode's account tokens filtered out; the screen shows only xcbeautify's digest (tasks with warnings or errors, test results) | already on the Mac; a failed build prints the log's path |

Header lines say which build the evidence came from; match them against `git log` before reading anything else — a
log from a build before the fix proves nothing about the fix.

## The session log

- **One file per launch**: `Documents/logs/grabber-<yyyyMMdd-HHmmss>.jsonl` in the app container, visible in the
  Files app. JSON Lines, one event per line: `{"type": "<event>", "t": <ms since launch>, ...fields}`. Numbers stay
  numbers. Writer: `native/App/SessionLog.swift`; what a line can carry: `SessionLogLine` in `ContextCore`.
- **Logs older than 30 days** are deleted at launch, except a file a report in `bugs.jsonl` names.
- **Crashes**: MetricKit payloads land in `Documents/crashes/<stamp>.json`; the app's own `signal-<epoch>.txt` and
  `exception-<epoch>.txt` cover the days MetricKit takes on a development build. Each is announced once as
  `crash_report`. A log that simply stops, with no crash file, is a kill from outside (memory).

```bash
just pull-logs                  # phone → ~/tmp/agent/grabber-logs/ (logs/, bugs.jsonl, bugs/<stamp>/, crashes/); the phone's id: DEVICE=<udid> or scripts/native/phone-udid.local
just pull-logs-sim              # simulator → ~/tmp/agent/grabber-logs/sim/
just log-summary <file.jsonl>
jq -c 'select(.t > 57000 and .t < 60000)' <file>     # around a moment (a report's session_t_ms)
just symbolicate ~/tmp/agent/grabber-logs/crashes/<stamp>.json
```

**Today's hand, the widget, has no session log** (#230). Its extension writes unified-log lines instead (subsystem
`com.idvorkin.grabbernative`, category `todays-hand`): `deal_tap` (old nonce, `shown`: the card the tapped widget showed by code such as `AH`, `on_screen`: its index in today's pool, new and stored nonce, pool size, slot,
and the card index from and to) when a tap on the card runs the intent, and `timeline` (nonce, pool size, the first
entry's index and card) each time the widget builds its timeline. A tap that changes nothing is one of three:
no `deal_tap` (the intent never ran), `deal_tap` with no `timeline` after it (the reload never came), or both with
the same card. The button carries the card it showed, so a skipped redraw, a card left up past its five minutes or a changed
*Skip easy cards* cannot make a tap deal that card again; `on_screen` is `none` when that card has left the pool. On the simulator:
`xcrun simctl spawn <udid> log show --last 10m --predicate 'subsystem == "com.idvorkin.grabbernative"'`; on the
phone, `log collect` from the Mac.

**From a shake to an issue.** A shake (or *Report a problem* behind the home screen's Settings tile) captures the window, and *Log it*
writes a `bug_report` event, a line in `Documents/bugs.jsonl` (note, screen, build, `log`, `session_t_ms`,
`screenshot`) and the picture under `Documents/bugs/<stamp>/`. The report dialog, the shake, the store and its
format are BugKit's (idvorkin/bug-kit). While Igor is on the phone, `just bugs-check` is BugKit's
`pull-reports.sh --check context-grabber`: it copies each plugged-in iPhone's and iPad's `bugs.jsonl` and prints
one line per report that is not yet an issue, `new context-grabber <device> <reported_at> <note>`, exiting 1 when
there are any (an unreachable device is named, not a failure).

**The listener files every report and crash; nobody files by hand.** BugKit's `listener/bug-listener` runs always
on, in the Herdr pane *listener/bug-listener*, and polls the phone and the iPad every five minutes (CG is in
`~/.config/bug-kit/apps.json`). Each new report or crash becomes one GitHub issue, carrying the note, the screen,
the build and the session log, with the screenshot's path on the Mac and no picture uploaded (the repo is public).
It copies the evidence to `~/tmp/agent/bugs/context-grabber/<device>/`, appends a line to
`~/tmp/agent/bugs/inbox.jsonl` and sends a Herdr notification. Its steps are in `~/tmp/agent/bugs/listener.log`.
So an agent never files a report itself; doing so would file it twice. Watch the inbox for this app instead, for
example `Monitor(command: "tail -n0 -F ~/tmp/agent/bugs/inbox.jsonl | grep --line-buffered context-grabber")`, and
fix what lands. Then follow steps 3–5 of *Bug reports* below, reading the log at the report's `session_t_ms`.

## Adding a line

`log.event("snake_case_type", ["field": value])`, and a row in the table above in the same change. Put the deciding
numbers in fields, not in prose; log a failure once per spell, not once per retry; log the boundary (armed, healed,
ended), not every tick. A screen-level failure is a copyable error with the relevant state passed along rather than a
log line — Igor copies it without opening anything.

## Instrument before theorizing

For any phone-only symptom: add the line that would settle it, ship it (`just native-run-device`), reproduce, pull
the logs, read the numbers, then fix. Never ship a second guessed fix. Examples that paid off: the mic-arm log of
other audio, route inputs and session shape that turned the silent first call from a guess into #95's evidence
(#102); the log written to disk as it goes so a freeze while switching microphones lost nothing (#106); the timer
log showing every cue requested and none heard while music was mixed in, which is why the cues are sound files and
not synthesis (2026-09-07).

## Bug reports: from the phone to a closed issue

1. **On the phone**: Igor hits it. He shakes the phone, copies the error, or says it in the session. The
   copied payload carries the build line, so nothing needs retyping.
2. **File it**: a shake report or a crash is filed by BugKit's listener on its own (above); never file one yourself.
   A report that arrives any other way (a copied error or log, or Igor's voice in the session) gets one GitHub issue
   (`gh issue create`) with the payload, the build line and what he was doing, so the trail is complete. Track the work in `bd` when it spans sessions; the issue is where the
   evidence lives and what the commit closes.
3. **Before fixing**: find or write the story in [stories/](stories/README.md) that the report belongs to — a bug gets
   an `Issues:` line, a request becomes a story, no story means the spec has a hole — and, when the behaviour will
   change, re-open the feature's design spec first (spec-first, [AGENTS.md](../AGENTS.md)). Then read the log at
   the moment of the report and put that evidence on the issue as a comment.
4. **Fix on the cheapest rung** that can see it ([TESTING.md](TESTING.md)): a host test that fails first when the
   logic is in `ContextCore`; a line in the log when it is the phone's. One PR per issue, referencing it.
5. **Ship and close**: `just native-run-device`. Close the issue once the build is on the
   phone (`Fixes #N` in the PR when the verifying rung already ran, otherwise by hand after the build landed) with a
   comment saying what was verified where and what Igor should feel; Igor reopens if it is not fixed. Never leave a
   fixed bug open.


## Device tooling

- `just native-run-device` builds under the Mac's signing lock and BugKit's screen-lock guard, then installs and
  launches over `devicectl`; the phone's id is `DEVICE=<udid>` or the gitignored `scripts/native/phone-udid.local`.
  A locked phone fails the launch step only; the install is done. If Xcode lost the Apple ID after an update,
  re-add it in Xcode → Settings → Accounts, and never run a signing build while the Mac's screen is locked.
- Each session log's first line (`session_start`: sha, branch) says which build is running.
