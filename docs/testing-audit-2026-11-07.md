## Findings

- **The Mac app is Mac Catalyst, not a separate native macOS/AppKit target.** `GrabberNative` is an iOS application with `SUPPORTS_MACCATALYST: YES`; the build explicitly selects `platform=macOS,variant=Mac Catalyst,arch=arm64`. The standalone `ContextCore` SwiftPM tests do run as macOS host tests, a different execution path. ([native/project.yml:33](../native/project.yml#L33), [native/project.yml:111](../native/project.yml#L111), [justfile:121](../justfile#L121), [native/ContextCore/Package.swift:4](../native/ContextCore/Package.swift#L4))
- **Today's automatic Mac rung runs zero tests and does not launch the app.** It invokes `native-build-mac`; the optional `native-run-mac` builds and uses `open`. One Catalyst-only keyboard UI test exists, but the documented ad hoc runner cannot load it and the test target does not explicitly enable Catalyst. There is no established Catalyst test-time speedup to report. ([scripts/native/test-ladder.sh:183](../scripts/native/test-ladder.sh#L183), [justfile:132](../justfile#L132), [native/UITests/MacKeysUITests.swift:1](../native/UITests/MacKeysUITests.swift#L1), [native/project.yml:177](../native/project.yml#L177), [docs/TESTING.md:13](TESTING.md#L13))
- **Host tests already carry most test cases:** 1,028 declared methods in 126 XCTest classes across 80 files, versus 132 simulator UI test slots across 49 classes (one slot is an intentional skip), plus one conditional Mac UI method. These are static totals from the complete per-file inventories below, not a successful discovery/run. The older “985 tests” in the testing guide is dated November 5. ([host inventory](#host-test-inventory), [ui inventory](#ui-test-inventory), [docs/TESTING.md:65](TESTING.md#L65))
- **The largest documented recurring cost is whiteboard UI automation:** 63 tests in 1,621 seconds in the story's recorded run; the guide now budgets about 28 minutes with the extra keyboard boot. Moving rules into host tests offers a better-supported speed hypothesis than merely changing the UI destination to Catalyst. ([docs/stories/11-building-and-testing.md:72](stories/11-building-and-testing.md#L72), [docs/TESTING.md:133](TESTING.md#L133), [docs/stories/11-building-and-testing.md:6](stories/11-building-and-testing.md#L6))
- **“Host” currently means Mac, not Linux.** The single SwiftPM source/test targets include Apple framework imports, Apple Foundation APIs and JavaScriptCore/PencilKit tests; `native-test-host` also compiles an asset catalog with Xcode tools. A Darwin cross-build validates compilation, not execution on Linux. ## Is testing on Catalyst much faster?

**Unproven for UI tests; well supported for extracting rules into macOS host tests.** The guide's warm host budget is ~25 s for the complete rung, against ~27–30 s per whiteboard UI case. The recorded profile attributes about a third to app-idle waits, a fifth to lifecycle, a fifth to accessibility lookup and a sixth to appearance waits, with almost none compiling or moving between tests. Catalyst may remove simulator boot/runtime overhead, but it still uses UI automation and real views, so those costs cannot be assumed away. The recorded incremental simulator compile was only 34 s; moving a 27-minute suite's build alone is not the main saving. ([docs/TESTING.md:12](TESTING.md#L12), [docs/stories/11-building-and-testing.md:6](stories/11-building-and-testing.md#L6), [docs/stories/11-building-and-testing.md:72](stories/11-building-and-testing.md#L72), [docs/stories/11-building-and-testing.md:145](stories/11-building-and-testing.md#L145))

Catalyst is useful as an **additional app integration destination**, not a blanket equivalent to iOS. This build excludes widgets/share dependencies and substitutes an inert Live Activity controller; its ad hoc entitlements omit iCloud/Health. The Mac spec also excludes background tracking/tasks and describes mouse/window/keyboard behavior separately. Native macOS `swift test` already exercises Apple libraries such as CoreText, JavaScriptCore and PencilKit without launching the Catalyst app; creating another native macOS app target is not necessary to use that rung. ([native/project.yml:80](../native/project.yml#L80), [native/project.yml:114](../native/project.yml#L114), [native/App/LiveActivity/LiveActivityControllerMac.swift:9](../native/App/LiveActivity/LiveActivityControllerMac.swift#L9), [native/Mac/AdHoc.entitlements:5](../native/Mac/AdHoc.entitlements#L5), [docs/superpowers/specs/2026-11-03-native-mac-app-design.md:53](superpowers/specs/2026-11-03-native-mac-app-design.md#L53), [docs/superpowers/specs/2026-11-03-native-mac-app-design.md:106](superpowers/specs/2026-11-03-native-mac-app-design.md#L106), [native/ContextCore/Tests/ContextCoreTests/WhiteboardTurnTests.swift:1](../native/ContextCore/Tests/ContextCoreTests/WhiteboardTurnTests.swift#L1), [native/ContextCore/Tests/ContextCoreTests/CockpitBridgeTests.swift:4](../native/ContextCore/Tests/ContextCoreTests/CockpitBridgeTests.swift#L4))

Proposed evidence before changing the default destination: on an idle Mac, record cold and warm build separately; run the same non-system scenarios against identical fakes on simulator and Catalyst; record execution, boot/launch, skips, signing failure, and queue time separately. Start with hook/log checks, because Mac runtime hooks already exist; first establish a supported Catalyst UI runner/signing configuration rather than assuming the current iOS UI target works. Use three warm repetitions and compare median and slowest time before claiming a speedup. This is a measurement proposal, based on the current build-only Mac rung and runner restriction. ([justfile:132](../justfile#L132), [native/project.yml:177](../native/project.yml#L177), [docs/TESTING.md:13](TESTING.md#L13), [scripts/native/test-ladder.sh:331](../scripts/native/test-ladder.sh#L331))
